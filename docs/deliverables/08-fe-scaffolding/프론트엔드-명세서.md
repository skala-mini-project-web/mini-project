# ARGUS 프론트엔드 명세서

## 목적

ARGUS frontend는 PM과 컴플라이언스 reviewer가 동일한 분석 데이터를 역할별 권한으로 처리하는 Vue 3 SPA다. 화면은 분석 결과만 보여주지 않고, 문서·공식 사실·RAG retrieval trace·검토 상태·운영 조치의 연결을 보여준다.

## 기술 구성

- Vue 3 + Vite
- Vue Router
- Pinia
- REST API adapter
- PDF.js / Tesseract.js: frontend 실험·보조 기능
- 실제 문서 추출·분석·RAG는 Spring·FastAPI·Ollama 서버가 담당
- UI icon: Phosphor Icons

## 실행 모드

### 실제 서비스 모드

- `VITE_USE_MOCK=false`
- Vue → Spring REST API → PostgreSQL/pgvector → FastAPI → Ollama
- Compose frontend는 기본적으로 실제 API mode로 build된다.

### Mock 모드

- UX·빠른 회귀 검증용
- localStorage 기반 mock store를 사용한다.
- Mock 결과는 실제 PDFBox, pgvector, Ollama 성공 근거가 아니다.
- 오래된 localStorage mock schema는 자동 초기화한다.

## 역할과 권한

### PM

- 상품 등록·조회
- 문서 업로드·추출 텍스트 확정
- 공식 사실 확인
- Persona + Red Team 분석 요청
- 분석 결과·RAG trace 확인
- 검토 요청
- 승인 GuardFit 가이드 확인

### reviewer

- 검토 queue 조회
- review 상세 확인
- Finding 승인·반려
- Risk Pattern 활성화
- GuardFit 생성·승인
- 감사 로그 조회

권한 없는 route는 dashboard로 이동한다. backend도 역할·소유권을 별도로 검증하므로 frontend route guard만으로 권한을 보장하지 않는다.

## 화면과 route

```text
/                                  역할 선택
/dashboard                         역할별 dashboard
/products                          PM 상품 목록
/products/:productId               상품 상세·문서 목록
/documents/:documentId             문서 추출·텍스트 확정
/products/:productId/analyze       분석 조건 선택
/analyses/:analysisId              분석 결과·RAG trace·검토 요청
/reviews                           reviewer 검토함
/reviews/:reviewId                 검토 상세·승인·반려
/risk-library                      Risk Pattern library
/guardfit                          GuardFit guide
/audit                             감사 로그
```

## 주요 화면 명세

### 역할 선택과 dashboard

- PM과 reviewer를 명시적으로 선택한다.
- dashboard는 실제 업무 상태를 보여준다.
- PM은 상품·분석·검토 상태를 확인한다.
- reviewer는 대기 검토 건수와 검토 작업으로 이동한다.
- reviewer queue는 local notification이 아니라 backend `PENDING` review 상태를 기준으로 표시한다.

### 상품 상세

- 상품 기본 정보와 최신 문서를 보여준다.
- 문서가 없는 상태에서는 하나의 `문서 업로드` 버튼만 표시한다.
- PDF/PPTX 업로드 후 문서 workspace로 이동한다.
- 문서가 이미 있으면 최신 문서 상태와 분석 진입점을 보여준다.

### 문서 workspace

- 업로드 파일명, 추출 상태, 추출 텍스트를 보여준다.
- 상태: `UPLOADED`, `EXTRACTING`, `READY`, `FAILED`
- PM은 `READY` 텍스트를 확인·확정한다.
- 실패 시 error·retryable 상태에 따라 재시도 UI를 제공한다.

### 분석 조건 선택

PM은 다음을 선택한다.

- 확정 상품 문서
- 활성 근거 문서 1~3개
- 공식 사실 확인
- Persona 1~4개
- Red Team Pack

분석 요청 버튼은 확정 문서, VERIFIED 사실, 근거·Persona 선택 범위가 모두 충족될 때만 활성화된다.

### 분석 결과

- risk score, Finding, severity, recommendation
- Finding별 Persona·근거 document·excerpt
- 공식 사실 snapshot
- RAG 검색 근거
  - embedding model
  - retrieval version
  - query hash
  - retrieved time
  - rank·similarity·source·exact excerpt
- PM 검토 요청 상태
  - 대기
  - 승인
  - 반려 및 reviewer comment

`COMPLETED`와 `IN_REVIEW` 분석은 모두 결과 화면을 유지한다.

### 검토 상세

reviewer는 다음을 함께 확인한다.

- PM 검토 요청 의견
- 분석 원문·공식 사실·Finding
- PM과 동일한 RAG retrieval trace
- 선택 Finding 수
- review comment

승인 시 Finding을 하나 이상 선택해야 한다. 반려 시 comment가 필수다.

### Risk Pattern과 GuardFit

- 승인된 Finding만 Risk Pattern으로 생성된다.
- reviewer가 Pattern을 활성화한 뒤 GuardFit 초안을 생성한다.
- GuardFit은 reviewer 승인 후 PM 화면에 보인다.
- 기존 Pattern은 삭제하지 않고 library에 보존한다.

## API adapter 원칙

`frontend/src/api/index.js`가 Mock과 실제 API의 경계다.

- 실제 응답 DTO를 UI model로 명시적으로 변환한다.
- demo user: `userId → id`
- review detail: `reviewId → id`
- document: `extractedText → rawExtractedText`
- analysis input: evidence/persona server ID를 UI ID로 변환한다.
- backend가 제공하지 않는 과거 이력은 frontend가 가짜로 생성하지 않는다.

## 사용자 경험 원칙

- 로딩 중에는 spinner 또는 skeleton을 표시한다.
- 실패 시 error message와 retry 가능 여부를 보여준다.
- 이전에 성공적으로 읽은 데이터는 재로딩 실패가 나도 즉시 비우지 않는다.
- mutating request는 중복 클릭을 막는다.
- API error는 toast와 화면 상태로 구분해 전달한다.
- 실제 review가 없는 초기 `REVIEW_NOT_FOUND`는 오류 화면이 아니라 검토 요청 전 상태로 표시한다.

## 실제 시연 확인 항목

1. PM으로 로그인한다.
2. 시연 PDF 업로드·텍스트 확정·공식 사실 확인을 진행한다.
3. 분석 결과의 RAG retrieval trace를 확인한다.
4. PM이 검토 요청을 보낸다.
5. reviewer로 전환해 같은 trace와 PM 의견을 확인한다.
6. 승인 또는 반려 흐름을 진행한다.
7. 승인 시 Risk Pattern과 GuardFit, 반려 시 PM 수정 필요 상태를 확인한다.

실제 브라우저 E2E script는 `frontend/scripts/real-rag-full-flow-e2e.mjs`다. API interception이나 mockServer를 사용하지 않는다.
